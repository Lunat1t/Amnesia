# Инструкции для агентов Galaxy

## Текущая цель

Ближайшая продуктовая цель — узкая основа Galaxy для разработчиков, работающих с Codex/LLM. Проверяем, помогает ли Galaxy накопить опыт одной работы и улучшить следующую. С 2026-10-03 действует исследовательская инициатива «Операция Амнезия»: максимально улучшить контекст и память агентов, активно собирать любые гипотезы и теории из смежных областей и превращать перспективные идеи в проверяемые эксперименты. Исследовательский охват может быть широким; принятый scope реализации Galaxy 5.0 остаётся Context, Memory, Experience, Skills/Learning и Evidence, пока решение о его изменении не подтверждено источниками и замерами. Codex, Claude и OpenCode остаются внешними execution runtimes.

Для ближайшей реализации читай [roadmap Galaxy 5.0](docs/galaxy-v5-roadmap.md). Для общего направления и объяснения команде читай [долгосрочную roadmap простым языком](docs/galaxy-long-term-roadmap.md). Не смешивай дальние идеи с обязательным объёмом 5.0.

## Перед работой

1. Прочитай [roadmap 5.0](docs/galaxy-v5-roadmap.md).
2. Открой [карту источников](docs/sources/galaxy-superapp/00-source-map.md) и нужные карточки.
3. Для утверждений о реализованном состоянии смотри [внутренние источники](docs/sources/galaxy-superapp/01-current-galaxy.md), затем проверь код. Не выдавай задуманные функции за работающие.
4. Прежде чем добавлять новые функции, проверь, можно ли улучшить текущий Codex MCP путь и существующий Context/Memory pipeline.

## Внешние Codex-агенты для разработки Galaxy

Владелец проекта выступает Product Manager и принимает продуктовые решения: пользовательская проблема, приоритет, выбор варианта и изменение scope. Основной Codex — координатор/техлид: сам уточняет техническую часть, подключает нужных специалистов, сводит выводы в короткий понятный brief и задаёт вопрос владельцу только при настоящем продуктовом выборе. Не требуй от Product Manager технических деталей, которые команда может исследовать самостоятельно; не переспрашивай разрешение на обычные шаги уже запрошенной реализации.

Для личной разработки доступны специализированные Codex subagents из [руководства команды](docs/codex-agent-workflow.md). Это внешние инструменты разработчика, не функции продукта Galaxy 5.0. Основной Codex работает по циклу attention map → маршрутизация → выполнение → auto-steering → review → outcome. Шаблон карты, playbook и incident register находятся в `docs/codex-harness/`; проектный guard hook описан там же и подключён из `.codex/config.toml`. Роли: `galaxy_product_partner`, `galaxy_researcher`, `galaxy_code_explorer`, `galaxy_experiment_designer`, `galaxy_reviewer`, `galaxy_implementer`. Подключай только нужных; сначала read-only разведка, один writer на пересекающиеся файлы; максимум 3 параллельных агента. Каждый делегированный агент получает нужные инструкции и source cards. Повторяющиеся коррекции становятся постоянным правилом только после evidence и проверки ложных срабатываний. Оркестратор не выбирает продуктовую цель за PM и не считает число агентов/артефактов результатом.

## Обязательная работа с источниками

- Это правило действует для всех агентов и субагентов, которые исследуют, проектируют, меняют или оценивают Galaxy. Передай его и ссылки на нужные карточки каждому делегированному агенту.
- Для каждой нетривиальной задачи сначала найди в карте источников карточки, относящиеся к вопросу, и прочитай их до предложений по архитектуре или изменений кода. Для задач по пяти основам проверь также [`docs/architecture/foundation.md`](docs/architecture/foundation.md); для архитектурных изменений — [`docs/architecture/current-state.md`](docs/architecture/current-state.md).
- Перед решением явно отдели три вида опоры: **внутреннее свидетельство** о текущем коде/замерах, **внешний источник** о чужом методе или результате, **гипотеза Galaxy**. Внешняя статья не доказывает, что функция Galaxy уже работает или будет полезной.
- Решение о новой функции, изменении архитектуры или продуктового scope должно указывать конкретные источники и объяснять, какую часть решения каждый источник поддерживает. Сверяйся с roadmap и ограничениями версии.
- Если источника нет, он слабый или не отвечает на вопрос, не заполняй пробел догадкой. Скажи, что подтверждено, что неизвестно, и предложи поиск/эксперимент. Не представляй теоретические зацепки из `06-research-leads.md` как принятые решения.
- Для заявлений о поведении Galaxy сверяй документацию с кодом и воспроизводимыми замерами. Для внешних фактов предпочитай первоисточники; дату, ссылку, происхождение и ограничения фиксируй в source note.
- В каждом содержательном плане, отчёте или завершении задачи укажи использованные карточки/источники и вывод, который они поддержали. Если источники не повлияли на механическую задачу, кратко отметь это, а не создавай фиктивную опору.

## Приоритеты и ограничения

- Сначала проверяй установку и качество существующей интеграции Codex/MCP; не начинай отдельное приложение раньше необходимости.
- Улучшай контекст, память, скорость, свежесть и стоимость на реальных coding-задачах.
- Не развивай агентные функции или orchestration внутри Galaxy, runtime, World Model и другие большие идеи в этой версии без измеримой необходимости для пяти основ. Персональные Codex subagents для инженерной работы ведутся отдельно по `docs/codex-agent-workflow.md` и не расширяют продуктовый scope.
- Навыки остаются evidence-backed кандидатами до независимой оценки и явной проверки; не активируй модельные правила автоматически.
- Не начинай отдельную Core/OS платформу, мобильное приложение, комнаты/заметочный UI, облачный SaaS, маркетплейс или широкую поддержку профессий до подтверждения пользы узкой основы.
- Сравнивай одинаковые задачи с Galaxy и без него по проверенному успеху, времени, токенам, стоимости, ошибкам retrieval и исправлениям.
- Сохраняй provenance и свежесть памяти. Не называй локальные owner/team поля настоящей авторизацией или SaaS-границей безопасности.
- Если меняется продуктовый фокус, обнови `docs/galaxy-v5-roadmap.md`, соответствующие source notes и эти инструкции.
- Для архитектурных изменений сначала читай [`docs/architecture/current-state.md`](docs/architecture/current-state.md) и [`docs/architecture/foundation.md`](docs/architecture/foundation.md). Текущий узкий scope — Context, Memory, Experience, Skills/Learning и Evidence.
- Не создавай отдельный большой Core/OS слой и не развивай остальные экспериментальные механизмы без необходимости для этих пяти основ. Не удаляй рабочий legacy код; если изменение нужно, сохраняй импортный compatibility слой и benchmark evidence.
